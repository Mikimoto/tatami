tatami 使用說明

macOS 的視窗管理工具：每個 space 一份版面、格線面板、⌥ ＋ 拖曳吸附，45 條可改的快捷鍵， 全部住在一個選單列 app 裡。

安裝

brew tap mikimoto/tatami
brew trust mikimoto/tatami
brew install --cask tatami

中間那行不能省。

Homebrew 7 起，第三方 tap 的 cask 預設不給裝。少了 brew trust 會停在 Refusing to load cask … from untrusted tap，而錯誤訊息本身就會告訴你 要跑哪一行。

這會裝好 /Applications/Tatami.app，並在 PATH 上放一個 tatami。 兩者是同一個執行檔——CLI 與選單列 app 永遠同版本，不會有一邊比較舊的問題。

需要 macOS 14（Sonoma）以上。

授權

tatami 要移動別的 app 的視窗，所以需要「輔助使用」權限。第一次開啟時系統會跳出對話框， 或者你自己去開： 

系統設定 → 隱私權與安全性 → 輔助使用 → 打開 Tatami

撥開開關之後要把 app 關掉再開一次。

macOS 的權限系統不會套用到已經在跑的行程。撥開之後不重開的話， 快捷鍵按下去沒反應、視窗也不會動——而畫面上看起來權限明明已經給了。

tatami 不需要「輸入監控」，也不需要關閉 SIP。它沒有沙盒——一個沙盒化的 app 拿不到操作別人視窗的權限。

第一次使用

裝完之後照這個順序走一次：

  1. 開啟 Tatami.app，撥開「輔助使用」，重開一次。
  2. 選單列會出現圖示。點開它 → 登入時自動啟動（不打開的話， 快捷鍵只在你手動開著它的時候有效）。
  3. 把視窗排成你想要的樣子。
  4. 選單列 → 把目前排版存進 ▸ → 挑一個 profile（或打一個新名字）。
  5. 之後切到那個 space，按 ⌃⌥⌘W 就排回去。

第 3、4 步是這個工具的核心：你不需要手寫設定檔。 把畫面排好、存起來，它會自己反推出版面樹與視窗規則。

設定檔在哪

~/.config/tatami/
├── layout.json      版面：地點、profile、每個 space 的樹、視窗規則
├── hotkeys.json     快捷鍵、格線設定、滑鼠拖曳、float 清單
└── .tatami-state    記住的地點與 profile、學到的頂端 inset

三個檔都是選配的。hotkeys.json 不存在就用內建的 45 條； .tatami-state 由程式自己維護，不必手改。

layout.json 的範本在 repo 的 examples/layout.json。 改完可以驗一下： 

tatami validate

它讀 ~/.config/tatami/layout.json，有問題就逐條指出來（哪個地點、哪個 profile、哪一棵樹）。從管線餵給它也可以：tatami validate < 別的檔.json。

地點、profile、space

設定是三層的，每一層回答一個不同的問題：

層回答什麼誰決定
地點
home / office		 我現在在哪？接了哪幾台螢幕？ 自動偵測，比對螢幕 UUID
profile
開發 / 會議		 我現在在做什麼？ 你指定（選單列或 --switch）
space 這個桌面要長什麼樣？ 每個 space 各一棵樹，靠 space UUID 索引

所以同一個 profile 在 home 與 office 可以有完全不同的版面—— 螢幕不一樣，版面本來就該不一樣。

螢幕角色

地點底下的 displays 把「角色名」對到螢幕 UUID： 

"office": {
  "desc": "公司",
  "displays": {
    "main":   "11111111-1111-4111-8111-111111111111",
    "second": "22222222-2222-4222-8222-222222222222"
  },
  ...
}

角色名是你自己取的（main 必須存在）。用角色而不是直接用 UUID， 是因為版面樹要講「主螢幕左半」而不是「那台特定的 BenQ 的左半」。

要查目前接了哪些螢幕與它們的 UUID：

tatami ws displays

每個 space 一份版面

profile 底下的 spaceTrees 是角色 → { space UUID → 一棵樹 }： 

"profiles": {
  "開發": {
    "trees": {},
    "spaceTrees": {
      "main": {
        "AAAAAAAA-0001-0000-0000-000000000001": {
          "axis": "vertical",
          "children": [ {"window": "編輯器"}, {"window": "終端機"} ]
        }
      }
    }
  }
}

trees 這個鍵不能刪，即使它是空的。

驗證會要求它存在。它是舊格式的殘留，現在沒有任何套版路徑會讀它——實際在用的是 spaceTrees。

space UUID 撐得過重開機，所以拿它當索引是安全的。 要查：tatami ws spaces。不過實務上你不必手打—— 用選單列存檔，它會自己填。

不在樹裡的視窗，一概不碰

這是 tatami 與傳統 tiling 工具最大的差別：預設什麼都不管。 只有寫進某棵樹的視窗才會被移動，其餘的照你擺的位置放著。

所以不需要維護一份「例外清單」。要加入管理就把它畫進樹裡，要退出就從樹裡拿掉。

視窗怎麼被認出來

樹的葉子寫的是「標籤」，標籤對到哪個視窗由 windows 陣列的規則決定： 

"windows": [
  { "label": "編輯器", "match": ["app", "Zed"] },
  { "label": "終端機", "match": ["app", "Ghostty"] },
  { "label": "文件",   "match": ["url-contains", "docs.example.com"],
                       "launch": "Safari" }
]
match 類型比對什麼
appapp 名稱，精確比對
url-exactSafari 分頁網址，完全相同
url-containsSafari 分頁網址，包含這段
title-regexSafari 分頁標題，ERE 正規表示式

後三種只看得到 Safari 的分頁。

它們讀的是 Safari 的分頁清單，所以 title-regex 配的是分頁標題， 不是視窗標題；別的瀏覽器的視窗這三種都認不到。

另外它們需要一次 Safari 分頁查詢（約兩秒），所以 tatami 只在「這一輪要套的樹真的 用到這類規則」時才付這個錢。

launch：要開哪個 app

app 類的規則自己就講了要開什麼。網址與標題類的沒有—— 一個 url-contains 規則要的視窗可能屬於任何瀏覽器，設定檔一個字都沒說。 launch 就是那句沒說的話，只有 tatami --space --launch 會用到它。

三層規則

windows 可以出現在三個地方，優先序是共用層 → 地點層 → profile 層：

  • 共用層（最外層）與地點層是疊加的。
  • profile 層不一樣——它一旦存在就整組取代前兩層。

規則是先到先得：同一個視窗被多條規則配到時，排在前面的那條贏。

版面形狀範例

三種以上的視窗就往下疊。axis 只有 vertical（左右切）與 horizontal（上下切）兩個值。

ratio 只能掛在葉子上。

它是「這個節點佔父節點的比例」，而程式只會讀第一個 child 的那一個。 所以 (A｜B) / (C｜D) 這種外層的分割線存不住比例—— 圖形編輯器會把那條線畫成不可拖曳，並在提示裡說明原因。

格線面板

按 ⌃⌥⌘G，焦點視窗所在的那台螢幕正中央會浮出一塊縮圖面板。 在上面拖一個矩形，放開，那個視窗就排到螢幕上對應的位置。

拖曳的時候真螢幕上會同步亮出目標區域，所以放開之前就看得到結果。

esc、原地按下放開（同一格）、或點面板以外的地方，都是取消。

兩個模式

面板右上角有三顆小按鈕：

按鈕做什麼
記 一個開關。先按它再拖，放開時不套用，而是把那塊位置存進位置庫。
格切回拖曳模式。
庫 切到位置庫：一面縮圖牆，每一格是存過的位置。點一下就套用，面板不關， 所以可以對同一個視窗連續試不同位置。每格右上角的 × 刪掉它。

格數與間距

預設 6 欄 × 4 列、間距 8，而且是每台螢幕各一份—— 27 吋跟筆電內建螢幕本來就該切得不一樣。在 tatami edit 的「格線」那一頁改。

臨時想用別的格數，旗標蓋得過設定：

tatami grid --columns 3 --rows 2

位置庫裡的每一格自帶格數，所以你把螢幕改成 8×5 之後， 一個存成「左半」的位置還是左半。

⌥ ＋ 拖曳

動作效果
⌥ ＋ 左鍵拖曳搬動視窗
⌥ ＋ 右鍵拖曳縮放（抓住哪一個象限就動哪一角，對角釘住）

拖的時候畫面上會浮出吸附區，游標所在那一區整塊變色，放開就吸進去。分三層：

  • 邊緣帶（較短邊的 15%）：兩軸都在帶內＝角落，田字四分之一； 只有一軸＝上下左右半邊。
  • 中間：這個 space 的版面樹的葉子。沒有樹的話就是整片。
  • 正中央（20% × 20%）：整片畫布。

吸附只擺位置，不寫進設定。縮放不吸附。 修飾鍵可以改（fn / cmd / ctrl / shift）， 在 tatami edit 的「快捷鍵」頁最底下。

預設是 ⌥ 而不是 fn，這是實測換來的。

在某些外接鍵盤上（例如有自己驅動程式的 Logitech），fn 由鍵盤韌體處理、 根本不會送到 macOS——三個獨立的 API 讀到的修飾鍵狀態全是 0。 如果你把修飾鍵改成 fn 之後完全沒反應，就是這個原因，換一顆即可。

快捷鍵只在 Tatami.app 跑著的時候有效。

註冊掛在行程上，行程結束註冊就沒了。所以「登入時自動啟動」從方便變成必要。

而且改完設定要把選單列結束再開一次——沒有做熱重載。

自己寫一條

動作欄可以填 shell: 加一條命令，它會交給 /bin/sh -c。 這是給「跟視窗管理無關，但我想綁一顆鍵」的東西用的逃生門。

至少要含 ⌘ / ⌃ / ⌥ 其中一個（⇧ 不算）。 原因很實際：註冊過的組合會被系統吃掉、不再往下傳，所以一個裸的 w 會讓你在每個 app 裡打字都變成重排視窗，而且沒辦法從那個 app 裡救回來。

圖形編輯器

tatami edit

側欄分頁：

頁編什麼存到
版面拖放編輯每個 space 的樹、規則表格、地點與 profilelayout.json
快捷鍵45 條綁定、float 清單、滑鼠拖曳設定hotkeys.json
格線每台螢幕的格數與間距、位置庫的改名與刪除hotkeys.json

⌘S 存檔，⌘Z 復原，⌘R 立刻把目前可見的 space 套成你編的樣子 （要先存檔——套版是從磁碟讀的，它不知道你記憶體裡有什麼）。

存檔前有三道閘門：

  1. 驗證——與 tatami validate 同一支。
  2. 外部變更比對——載入時記下原文，寫之前重讀一次。 這個檔常被手改，也會被 --save 與格線面板寫。
  3. 原子寫——寫暫存檔再換上去，中途斷電不會留下半個檔。

常用命令

命令做什麼
tatami --space 把目前可見的 space 排成設定好的版面
tatami --space --all 排每一個有版面的 space，不只看得見的那個
tatami --space --launch 同上，並把樹裡引用到、而沒在跑的 app 開起來
tatami --probe 只辨識不動視窗：印出哪個視窗被認成哪個標籤
tatami --save [profile] 把目前的排版存起來（終端機會逐一問視窗名稱）
tatami --save --all 存每一個有視窗的 space
tatami --switch 互動式切換地點 / profile
tatami validate 檢查設定是否合法
tatami edit圖形編輯器
tatami grid格線面板
tatami ws displays / ws spaces / ws windows 列出螢幕 / space / 視窗，印 JSON

拔插螢幕之後用 --all。

macOS 會在拔插之後重排哪個 space 在哪台螢幕、哪個可見。 此時 --space 只排「你正在看的那一個」，而你要找的視窗很可能在旁邊 某個不可見的 space 上——那就是「跑了卻什麼都沒動」的成因。 --space --all 排的是每一棵有樹的 space。

疑難排解

按了快捷鍵什麼都沒發生

  1. Tatami.app 在跑嗎？（選單列有沒有圖示）
  2. 「輔助使用」撥開了嗎？撥開之後有沒有重開 app？
  3. 那個組合被別的 app 佔走了嗎？選單列的 log 會說「另有 N 組被系統或別的 app 佔走」。
  4. 剛改完 hotkeys.json？要結束選單列再開一次。

切過去那個 space，版面沒有套用

  • 那個 space 有畫過版面嗎？tatami --probe 會說「這個 space 還沒有版面，跳過」。
  • 「切換 space 自動重排」的開關打開了嗎？（選單列，預設是關的）
  • 樹裡的 app 沒在跑的話，那一格會靜默空著。用 --space --launch 開它們。

視窗排好了，但尺寸不對

app 可以拒絕你給的尺寸（很多 app 有自己的最小寬高）。tatami 會回報 frameRejected 並印出它實際拿到的數字——那不是 bug，是那個 app 的下限。

頂端空一條，怎麼排都在

每台螢幕的選單列高度沒有任何 API 吐得出來，所以 tatami 是自己學的， 學到的值寫在 .tatami-state 的 topinset.<螢幕 UUID>。 學錯了（例如在某次異常的排版中取樣到）就把那一行刪掉，讓它重新學。

0.1.1 以前這一條會扣兩次：畫布的頂端取自 NSScreen.visibleFrame， 而 AppKit 只在選單列當下所在的那台螢幕上扣掉它，學到的值又扣一次。主螢幕一換 （關筆電蓋、拔插螢幕、改排列）排滿的樹就上下各空一條。0.1.2 起頂端一律取自螢幕的 原始 frame，選單列只剩自動校準這一個來源。

升級之後，還沒學過的螢幕第一次排版會各印一句 沒有接受指定的位置——那一列被 macOS 往下推，而 tatami 正是靠這個學。 第二次就精確了，訊息也會消失。

tatami validate 說舊格式

2026-08-30 之前 spaceTrees 是用「space 名字」索引的，現在改用 space UUID。 驗證會擋下舊格式並說明要改成什麼——不擋的話它會靜默失效（查表只認 UUID）， 設定看起來寫好了而功能就是不動。

設定不見了

設定住在 ~/.config/tatami/，與程式完全分開。 brew uninstall --cask tatami 不會碰它；只有 brew uninstall --zap --cask tatami 才會連設定一起刪。
